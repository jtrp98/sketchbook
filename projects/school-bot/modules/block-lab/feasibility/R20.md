## ข้อ (1) ขนาดบล็อกมน/หกเหลี่ยมในช่องฟังก์ชัน (OQ187 · OQ97 · design-taste 13)

**ทำได้** · ตรงกับ OQ97 (สูง 34 เท่ากันทุกที่) · D1 v328 (`design/D1-editor.md` §ขนาดบล็อก) อ้างต้นเหตุ: `rowSize` ใช้ความสูงลูก (34) เป็นความสูงแถว → แถบ 50 และตัวมนซ้อนโต 34→40 · แก้ให้ช่องที่มีลูกนับ 28 เท่าช่องว่าง ใช้กับทุกช่อง ทั้งทรงมนและหกเหลี่ยม · **ต้นเหตุยืนยันจากโค้ดเท่านั้น ยังไม่ render** (OQ187 เองระบุให้ดูบน canvas ก่อน)

**เงื่อนไข / edge case:**
1. **ตัวชี้วัดตรวจรับ (AC):** วัดความสูงบล็อกมน 1 ตัวและหกเหลี่ยม 1 ตัวใน 7 ที่ = 34 ทุกที่ (รายการ · พื้นที่ต่อบล็อก · ขณะลาก · ในช่องคำสั่งปกติ · ช่อง hat "รับค่า" · ช่อง "เรียก" · ช่อง "คืนค่า") และความสูงบล็อกแม่ก่อน/หลังใส่ลูกต้องเท่ากัน (ไม่ reflow ตอนวาง/ลาก) · ตรวจทั้งแม่ที่เป็นบล็อกคำสั่ง (44) และ hat
2. **ลูก 34 ในช่อง 28 (ยื่นเกิน 3px บน/ล่าง):** ใน D1 ช่องว่างสูง 28 ส่วนตอนมีลูกสูง 34 ผู้ใช้อาจเห็นว่าช่องว่างกับช่องที่เติมแล้ว "ขยาย" 6px (ตรงข้ามกับ design-taste 13) แม้แถวแม่ไม่ขยาย · ข้อเสนอ: ช่องที่รับบล็อกมน/หกเหลี่ยมสูง 34 ตั้งแต่ตอนว่าง (แถวคำสั่ง 44 = 34 + padding 5 + 5 พอดี) ช่อง text/dropdown/chip คง 28 · ถ้าตา OK กับ 28 คงไว้ · → **OQ195 (ข)**
3. **ซ้อนมนในมน (เลขคณิต เช่น (a + b) × c):** ลูก 34 อยู่ในแม่ที่สูง 34 เท่ากัน = ลูกทับขอบบน/ล่างของแม่ ไม่เหลือที่ให้เห็นทรงแม่ (เห็นแค่ปลายซ้ายขวา) · ทางเลือก (ก) คงทับ + ขอบแม่หนา 2px เข้ม (ข) แม่ที่มีลูกสูงขึ้นเป็น 42 (ขัด OQ97 "ไม่มีการเปลี่ยนขนาด" แต่ตรงแบบ Scratch/Mixly) · Proposed (ก) แล้ว render ดู ถ้าแยกทรงไม่ออกค่อยถามผู้ใช้เลือก (ข) → **OQ195 (ก)**
4. หกเหลี่ยมซ้อนหกเหลี่ยม (ถ้า-และ-หรือ) เรื่องเดียวกับข้อ 3 + ปลายแหลมกินความกว้าง (h/2+4) ต้องวัดความกว้างตอนซ้อน 3 ชั้น
5. ลูกลาก "ตอนลาก" ต้องเป็น 34 เช่นกัน (ชั้นลาก) · ตรวจ 2 ทรง (ผู้ใช้สั่งให้ตรวจหกเหลี่ยมด้วย)
6. ข้ามขั้น: D1 ถูกแก้ก่อน ruler ตรวจ (บันทึกใน INDEX "สถานะ" 2026-10-29) · ผลรอบนี้ไม่ขัดการแก้นั้น

## ข้อ (2) ปุ่ม 3 สี = ปุ่มระบบ macOS 100% (OQ188 · OQ189 · brand §11.5)

**ทำได้มีเงื่อนไข** · ไม่ block (ผู้ใช้ตัดสินแล้ว · ข้อยกเว้นเป้ากด ≥ 44 / 3:1 ตาม brand §11.5 บันทึกแล้ว)

**ข้อเท็จจริงที่ใช้ (ให้ dev ยืนยันกับเวอร์ชัน Electron จริง):**
- Electron วาดปุ่ม native ได้ด้วยส่วนหัวซ่อนชื่อ (`titleBarStyle: 'hidden'`/`'hiddenInset'` + `trafficLightPosition`) · DOM ของแอปเริ่มใต้แถบเดียวกัน (ไม่วาดวงกลมเอง) → OQ189 (ก) = **ได้** · ที่ว่างซ้ายต้องเว้นตามตำแหน่งปุ่ม
- ธรรมเนียม macOS: ปุ่มเขียว = **เต็มจอ** ไม่ใช่ขยาย/คืนขนาด · ตั้ง `fullscreenable: false` แล้วปุ่มเขียวจะทำหน้าที่ซูม (ขยาย/คืน) ตรง OQ119 · ถ้าไม่ตั้ง: เข้าเต็มจอแล้วปุ่มหายจนเอาเมาส์ขึ้นขอบบน และ header ต้องคืนที่ว่างซ้าย
- หน้าตาปุ่มเปลี่ยนตามเวอร์ชัน macOS (ภาพอ้างอิง "ไล่เฉดมีขอบบางเข้มกว่า" เป็นสไตล์รุ่นเก่า รุ่นใหม่ปุ่มโตกว่า/ต่างสไตล์) · "100% ตามระบบ" จึง**ไม่เท่ากับภาพอ้างอิงทุกเครื่อง** (หลัก design-taste ข้อ 9 ห้ามลักไก่ ต้องบอกผู้ใช้) · ความกว้างที่เว้นจึงวัดจากเครื่องจริงทุกเวอร์ชันที่รองรับ (ค่าเว้น 84 เป็น**ประมาณ** ไม่ได้วัด)
- ปุ่ม native ใช้ได้กับ VoiceOver (ชื่อตามภาษาระบบ) และมีคีย์ลัด ⌘M/⌘W ถ้าเมนูแอปมี role หน้าต่างครบ → ต้องไม่ลบเมนู Window (2.1.1) · WCAG 2.5.8/1.4.11 ไม่เป็นข้อบังคับกับ window chrome ของระบบ (ไม่ใช่เนื้อหาเว็บ) แต่ความเสี่ยงต่อ ป.3 คือวงกลมเล็ก ผู้ใช้ยอมรับแล้ว
- ปุ่มแดง native ต้องเข้า flow ปิดเดิมของ app-shell (ดัก `close` → dialog หยุดหุ่น/งานยังไม่ขึ้นคลาวด์) · ⌘Q ต้องผ่านทางเดียวกัน
- พื้นที่ลากหน้าต่าง: ส่วนหัวทั้งแถบเป็น drag region ยกเว้นปุ่ม/ช่อง (no-drag) · ดับเบิลคลิกส่วนหัว = ซูมตามระบบ (ต้องตัดสินว่าเปิดไหม)
- canvas วาดปุ่ม native ไม่ได้ → ภาพออกแบบเป็นภาพจำลองกำกับว่า "ปุ่มจริงโดยระบบ · ตำแหน่ง/ขนาดประมาณ" (ห้ามนับเป็น 100% ใน design)
- หน้าต่าง inactive ปุ่มเป็นเทา (พฤติกรรมระบบ · OQ189 ง) → ไม่ต้องออกแบบ · แต่ header ส่วนที่เหลือต้องมีสถานะ inactive ของตัวเองด้วยไหม → ปล่อยตามเดิม (ไม่เปลี่ยน)
- ขั้นต่ำ 1440×900 (OQ119) ชนจอ Mac เล็ก (พื้นที่ใช้ได้หลังเมนูบาร์/Dock อาจต่ำกว่า 900) · เรื่องเดิม ไม่ใช่ของรอบนี้ แต่ปุ่ม native ทำให้ผู้ใช้ย่อให้เล็กลงเองไม่ได้ถ้าล็อกขั้นต่ำ

**Windows (OQ189 ค):** ผู้ใช้ตอบเฉพาะ Mac · ตัวเลือก: (ก) `titleBarOverlay` = ปุ่มระบบ Windows จริง (กว้าง ~46 สูงตามแถบ 60 → เป้ากด ≥ 44 ผ่าน · มี Snap Layouts บน Windows 11 · ปรับสี/สัญลักษณ์ได้เล็กน้อย = ไม่ 100% เท่า Mac) (ข) คง DOM §11.5 เดิม (48×44 ตาม CI · tooltip · ไม่มี Snap Layouts ต้องเขียนคีย์บอร์ดเอง) · **Proposed: (ก)** ให้สอดคล้องหลักเดียวกับ Mac ตามที่ session หลักเสนอใน OQ189 · ไม่ block (ผู้ใช้ตัดสิน)

**ข้อขัดแย้ง X39:** `modules/app-shell/requirements.md` บรรทัด 33–35 (Mac ปุ่มกลม 28 · AUD-F05 44×44 · สี #FF5F57/#FEBC2E/#28C840 · ไอคอน #14243D เห็นตลอด · ปุ่ม "ซ่อน" ซ้ายสุด) และ DSG-11 ขัดกับ R20 (2)/brand §11.5 ที่ผู้ใช้ตัดสินแล้ว · brand §11.5 ถูกแก้แล้วแต่ app-shell ยังไม่ · session หลักแก้ตามกฎเปลี่ยน requirement (ผลถึง app-shell R2 และ R11 ของ block-lab)

## ข้อ (3) เปลี่ยนหมวดแล้วแผงรายการบล็อกที่ซ่อนต้องแสดง (OQ190 · OQ112 · OQ133 · design-taste 14)

**ทำได้** · เป็น H1 (สถานะระบบ) และ H4: การกดหมวดต้องเห็นผล

**ข้อเท็จจริงเอกสาร (แก้ข้อความ OQ190):** OQ133 ไม่ได้ให้ซ่อน/แสดงด้วยคลิกพื้นที่ว่าง "เท่านั้น" (มีปุ่มซ่อนในหัวรายการ + ที่จับตอนซ่อน + Esc) · ส่วนที่ขาดจริงคือ **OQ112 (ข) Proposed "กดปุ่มหมวดเปิดคืน"** ซึ่งเปิดค้างอยู่และ D1 ไม่ได้ทำ → R20 (3) = ยืนยัน OQ112 (ข) · **ข้อขัด X40:** R2 (12) เขียนแค่ "ซ่อน/แสดงด้วยการคลิกพื้นที่ต่อบล็อก" ต้องเพิ่ม "และเมื่อเลือกหมวด" (session หลักแก้ถ้อยคำ)

**เงื่อนไขและ edge case (ผู้ใช้ตัดสินหลักการแล้ว ที่เหลือเป็น Proposed):**
1. กดหมวดตอนซ่อน (หมวดไหนก็ตาม รวมหมวดที่เลือกอยู่) = เปิดแผงที่หมวดนั้น · ไม่นับเป็น "คลิกพื้นที่ว่าง" (ห้าม event ทะลุ)
2. **ข้อเสนอเปลี่ยน (ต่างจาก Proposed ใน OQ190):** กดหมวดที่เลือกอยู่ซ้ำตอนเปิด = **ไม่ทำอะไร** ไม่ปิด เหตุผล: ผู้ใช้ ป.3 กดซ้ำเพื่อ "ดูบล็อก" ตามหลัก design-taste 14 การที่แผงหายคือการกระทำเงียบแบบกลับด้าน · ปิดมีทางอยู่แล้ว (คลิกพื้นที่ว่าง · ปุ่มซ่อน · Esc) · ทางเลือก: toggle แบบ VS Code (เด็กไม่คุ้น) → ผู้ใช้เลือก
3. เลื่อนโฟกัสหมวดด้วยลูกศร = ยังไม่เปิด จนกด Enter/Space (ตาม Proposed เดิม · tab แบบ manual activation) · เลื่อนรายการหมวดอย่างเดียวไม่ใช่การกระทำ
4. โฟกัสหลังเปิด: อยู่ที่ปุ่มหมวดต่อ (ไม่ขโมย) ให้กด Tab เข้าแผง (แผงเอา `inert` ออกก่อน Tab ถึง) · Esc ตอนโฟกัสอยู่ที่หมวดหรือในแผง = ปิด และคืนโฟกัสที่หมวด (WCAG 2.4.3) · ประกาศ aria-live "แสดงรายการบล็อก หมวด …" (S14)
5. หมวดว่าง (6 จาก 15) ก็เปิดแผงพร้อมข้อความนำไป Sensor/ปุ่มกระโดด (OQ169) ไม่ใช่เงียบ
6. ระหว่างจำลอง: เปิด/ซ่อนแผงไม่ใช่การแก้ ไม่หยุดจำลอง (R10) · ขณะกำลังลากบล็อก: กดหมวดไม่ได้อยู่แล้ว
7. reduced-motion: แผงโผล่ทันทีไม่เลื่อน · แผงลอยทับบล็อกที่ผู้ใช้ดูอยู่ (พื้นทึบ 90%) ยอมรับตามแบบ flyout ของ Scratch/mBlock
8. แผงขวา (OQ102) เปิดอยู่: ใช้ข้อตกลง OQ112 (จ) เดิม

## ข้อ (4) ระบบ syntax อัจฉริยะในโหมดโค้ด (OQ191 · R3 · OQ152 · design-taste 11 · brand §11.18–11.19)

**ทำได้มีเงื่อนไข** · ไม่ block

**ขอบเขตกับของเดิม:** D1 §2.2 ทำ autocomplete แล้ว (รายการใต้เคอร์เซอร์ ≥ 1 ตัวอักษร · แหล่งคำ = ฐานความรู้เดิมของตัวเช็ก + ค่าคงที่ + ชนิด + คำควบคุม + ชื่อที่ผู้ใช้ตั้ง) → "แนะนำระหว่างพิมพ์" กับ "suggest จากที่พิมพ์ค้าง" **คือรายการเดิม** ไม่ต้องมี UI ใหม่ · ของใหม่จริงมี 2 อย่าง: (ก) **สีตามกลุ่มคำ** (ข) **ตัวจับคู่ที่ฉลาดขึ้น** (ไม่สนตัวพิมพ์เล็ก/ใหญ่ เช่น `pinmod` → `pinMode` · ท้ายคำ เช่น `Write` → digitalWrite) · ทั้งคู่ใช้ฐานคำชุดเดียวกัน (ความจริงข้อเดียว) · ไม่เรียกตัวเช็ก `analyze` ตอนพิมพ์ (D1 ยกเลิก realtime แล้ว · ตรง design-taste 11 ไม่เตือนก่อนเวลา) · การลงสีเป็นการแยกคำ (lexical) ไม่ใช่การแยกไวยากรณ์ → ไม่ต้องรู้ว่า `pinMode(13)` ผิดจำนวนอาร์กิวเมนต์

### (1) เมธอดหลังจุด: ตารางคลาสคงที่พอไหม

**ตารางคงที่อย่างเดียวไม่พอ** · ใช้ได้กับ object สำเร็จรูปที่มีชื่อเดียวในระบบ (`Serial`, `Wire`, `SPI`, `EEPROM`) แต่ไลบรารีที่เด็กใช้จริงบน Uno เป็นคลาสที่ต้องประกาศตัวแปร (`Servo s;` · `SoftwareSerial bt(2,3);`) และโค้ดที่ตัวสร้างใส่ให้เอง (OQ25) ก็ประกาศ `Servo` เป็นตัวแปร → ถ้าไม่รู้คลาสของตัวแปร `s.` จะไม่มีรายการเลย ทั้งที่เป็นกรณีที่พบบ่อยที่สุด · D1 ตารางกลุ่มสีเขียนว่าลงสี `<ตัวแปร Servo>.xxx` อยู่แล้ว แปลว่าตัวลงสีต้องรู้ชนิดตัวแปรอยู่ดี

**ไม่เกินตัวเช็กกฎจำลองถ้าจำกัดรูปแบบ:** หาชนิดด้วยการสแกนคำ (lexical) แบบเดียวกับที่ autocomplete เก็บ "ชื่อที่ผู้ใช้ตั้ง" อยู่แล้ว ไม่ต้องมี parser/compiler: รูปแบบ `<คลาสที่รู้จัก> ชื่อ[ (อาร์กิวเมนต์)] [, ชื่อ …] ;` ที่ใดก็ได้ในไฟล์ (ไม่สนขอบเขตตัวแปร)

**Proposed MVP (→ OQ201):**
| รองรับ | ไม่รองรับใน MVP (ไม่มีรายการ · ไม่ใช่ error · ดำปกติ) |
|---|---|
| object สำเร็จรูป: `Serial` `Wire` `SPI` `EEPROM` | อาร์เรย์ `Servo s[2]; s[0].` · pointer `->` · `auto` |
| ตัวแปรที่ประกาศด้วยคลาสในรายการ Uno (ข้อ 5) รวมหลายชื่อในบรรทัดเดียว | ตัวแปรที่ประกาศในพารามิเตอร์ฟังก์ชัน / struct ของผู้ใช้ |
| `String` (ตัวแปร `String msg;` → `length` `indexOf` `toInt` …) | ชื่อเดียวกันประกาศสองชนิดในต่างขอบเขต (ใช้ตัวแรก) |

- สี: เมธอดที่รู้จักหลังคลาสที่รู้จัก = มะกอกหนา (กลุ่มฟังก์ชัน Arduino) · เมธอดที่ไม่อยู่ในตาราง + `(` = ส้มปกติ (กติกา "การเรียก" ข้อ 3) · ชื่อตัวแปร (`s`) = ดำปกติ (ชื่อที่เด็กตั้ง)
- รายการขึ้นทันทีหลังพิมพ์ `.` (ตาม Arduino `activateOnTyping`) · ในคอมเมนต์/ข้อความยังขึ้นตามที่ผู้ใช้เลือกไม่งด (OQ200) แต่**ไม่ลงสี**ในคอมเมนต์/ข้อความ (D1 เดิม) → ไม่ขัด เพราะคนละกลไก
- เด็กประกาศตัวแปรทีหลังที่ใช้ (`s.` อยู่บนบรรทัดก่อน `Servo s;`) ก็ยังรู้ เพราะสแกนทั้งไฟล์ · ลบบรรทัดประกาศ → รายการหาย สีกลับเป็นส้ม/ดำ ทันที (ปกติ ไม่ใช่ error)
- `#include <Servo.h>` ไม่ใช่เงื่อนไขของรายการ (เด็กลืม include ได้ · compile ฟ้องตอนแปลงโค้ดเหมือนเดิม · H9 ข้อความ Output ภาษาเด็ก "ต้องมีบรรทัด #include <Servo.h>")

### (2) snippet + Tab ไปช่องถัดไป กับ Tab ของ autocomplete และ 2.1.1/2.1.2

**ซ้อนกันจริง แก้ได้ด้วยลำดับความสำคัญชัดเจน** · ตอนนี้ D1 §2.2: Enter/Tab = ใส่คำ · Esc = ปิดรายการ · Tab ถัดไป = ออกจากช่องโค้ด (ทางออก 2.1.2) · snippet เพิ่มสถานะที่สาม "อยู่ในช่องพารามิเตอร์" ที่จับ Tab ไว้อีกชั้น

**Proposed ลำดับ (→ OQ202):**
1. รายการ autocomplete เปิด → Tab/Enter = ใส่คำที่เลือก (ถ้าเป็นฟังก์ชัน = ใส่ snippet แล้วเข้าช่องที่ 1)
2. อยู่ใน snippet และรายการปิด → Tab = ช่องถัดไป · Shift+Tab = ช่องก่อน · Tab ที่ช่องสุดท้าย = จบ snippet วางเคอร์เซอร์หลัง `)` (ไม่ออกจากช่องโค้ด) · Esc = จบ snippet ค้างค่าที่พิมพ์ไว้
3. ไม่มีรายการและไม่อยู่ใน snippet → Tab = ออกจากช่องโค้ด (ตามเดิม)
- ในช่องพารามิเตอร์ autocomplete ขึ้นได้ (เช่น พิมพ์ `HI` → `HIGH`) → ข้อ 1 ชนะ · Esc ครั้งแรกปิดรายการ ครั้งที่สองจบ snippet ครั้งต่อมาไม่มีผล แล้ว Tab ออก → **ไม่เป็นกับดัก (2.1.2)** เพราะทางออกคือ Esc ซ้ำ ≤ 2 ครั้ง + Tab และทางนี้ต้องบอกใน `aria-describedby` ของช่องโค้ด
- ประกาศ aria-live ตอนเข้า snippet: "digitalWrite · ช่อง 1 จาก 2: ขา · Tab ไปช่องถัดไป · Esc ออก" (ไม่ประกาศทุกตัวอักษร) · ช่องที่เป็นอยู่ต้องมองเห็น (กรอบ/พื้น ≥ 3:1 · 1.4.11) ไม่ใช่สีพื้นจางอย่างเดียว
- เมาส์/แตะที่อื่นในโค้ด = จบ snippet · เลิกทำ (Ctrl+Z) ทั้ง snippet เป็น 1 ขั้น
- **ค่าในช่อง (H5 ป้องกันผิด):** ตัวอย่าง Arduino ใช้ชื่อพารามิเตอร์ (`${pin}`) ซึ่งถ้าเด็กไม่แก้จะ compile ไม่ผ่าน · Proposed: ใส่**ค่าเริ่มต้นที่ถูกต้องเสมอ** (`digitalWrite(LED_BUILTIN, HIGH)` · `delay(1000)` · `Serial.begin(9600)`) ส่วนชื่อพารามิเตอร์/คำอธิบายไทยอยู่ในคำใบ้ของรายการและในประกาศ · เด็กกดผ่านได้ทันทีโดยโค้ดยังถูก
- snippet ใส่ `( )` ให้แล้ว: เด็กพิมพ์ `(` หรือ `)` ซ้ำตรงจุดนั้นให้พิมพ์ทับ ไม่ซ้อน `((` · ไม่ใส่ `;` ให้ (เด็กเรียนพิมพ์เอง · ตรงตัวแก้มาตรฐาน)
- ฟังก์ชันไม่มีพารามิเตอร์ (`millis()`) ใส่ `()` แล้วเคอร์เซอร์หลัง `)` ไม่เข้าโหมด snippet

### (3) ส้ม = คลาส builtIn และการเรียกที่สะกดผิด

**ผ่าน WCAG 1.4.1 ในทางเทคนิค มีความเสี่ยงความหมาย (ไม่ block)** · สองกรณีต่างกันด้วยน้ำหนัก: `Serial` ส้ม **700** · `Delay(` ส้ม 400 · ข้อมูล "รู้จัก/ไม่รู้จัก" ถูกส่งด้วยน้ำหนัก (ไม่ใช่สี) จึงไม่ขัด 1.4.1 · แต่สำหรับ ป.3–4 ตัวหนา 700 กับ 400 ในตัวอักษร monospace 16px ต่างกันไม่มาก เด็กอาจอ่าน "ส้ม = ถูก" ทั้งคู่
- ข้อเท็จจริงที่ช่วย: (ก) คลาสขึ้นต้นด้วยตัวใหญ่และตามด้วย `.` หรือชื่อตัวแปร ไม่ตามด้วย `(` ส่วนกรณีสะกดผิดตามด้วย `(` เสมอ → รูปร่างโค้ดต่างกันอยู่แล้ว (ข) ส้มปกติไม่ได้แปลว่า "ผิด" แต่แปลว่า "เรียกสิ่งที่ไม่อยู่ในพจนานุกรม" ซึ่งรวมฟังก์ชันที่เด็กเขียนเอง (`blink()`) ที่ถูกต้อง → ความหมายจริงของส้มปกติคือ "การเรียก" ตามแบบ Arduino ไม่ใช่สัญญาณผิด (ตรง design-taste 11 ไม่เตือนก่อนเวลา) · สัญญาณผิดจริงยังอยู่ที่ Output ตอนแปลงโค้ด (H9)
- **ตัวหนาพอไหม:** พอสำหรับ "รู้จัก" ตามที่ผู้ใช้ตัดสิน ถ้าใช้ฟอนต์ monospace ที่มีหน้าตัวหนาจริง (D1 ข้อ IME 3) · ห้ามตัวหนาสังเคราะห์ · ไม่เสนอเพิ่มเส้นใต้/หยัก (ขัด OQ191 · design-taste 11)
- **ต้องระวัง (เงื่อนไขให้ crayon/dev):** กฎ "ชื่อ + `(` = การเรียก" ต้องยกเว้น keyword (`if (` `for (` `while (` `switch (` `sizeof(`) ให้เป็น teal ก่อน · การประกาศฟังก์ชัน `void blink()` ชื่อก็ตามด้วย `(` → ส้มปกติเหมือนตอนเรียก (สม่ำเสมอ ตรง Arduino) · ระหว่างพิมพ์ `delay` ครบแล้วยังไม่มี `(` = มะกอกหนา (รู้จัก) ไม่ต้องรอ `(`

### (5) รายการคำ Uno: เกณฑ์คัดและคลาสที่ควรมีตารางเมธอด

**เกณฑ์คัด (คำต้องผ่านทุกข้อ):**
1. compile ได้บน Arduino Uno (AVR ATmega328P) ด้วย Arduino AVR core ทางการ
2. อยู่ใน core หรือไลบรารีที่มากับ IDE สำหรับ AVR หรือไลบรารีที่ตัวสร้างโค้ดของบล็อก (โหมดบล็อก) ใส่ `#include` เอง (ความจริงข้อเดียวกับแท็บ "โค้ด C++")
3. ตัดของบอร์ดอื่น/ของเก่า: Bridge/Yun, Esplora, GSM, Robot, WiFi/WiFi101/WiFiNINA, USB `Keyboard`/`Mouse` (Uno ไม่เป็น HID), `Serial1`–`Serial3` (Uno มี Serial เดียว), `analogReadResolution`/`analogWriteResolution` (Due/Zero), `analogReference(INTERNAL1V1)` (Mega) ฯลฯ
4. คำเหล่านี้ไม่ลงสี → ดำ/ส้มปกติ = "ไม่รู้จักใน Uno" ซึ่งตรงความจริง (`Serial1.begin` ตาม `.` = ดำปกติ)

**คลาสที่ควรมีตารางเมธอด (Proposed MVP · → OQ201):**
| คลาส | ที่มา | ตัวอย่างเมธอด | เหตุผล |
|---|---|---|---|
| `Serial` (object) | core | begin print println available read write flush | บล็อก Serial + แผง Output (R8) |
| `Servo` | ไลบรารี IDE | attach write read detach attached writeMicroseconds | servo ในตารางเซนเซอร์ #33 + OQ25 |
| `String` | core | length indexOf substring toInt charAt equals concat trim | ชนิดในกล่องเฟือง (OQ183) |
| `Wire` (object) | ไลบรารี IDE | begin beginTransmission write endTransmission requestFrom read available | อุปกรณ์ I2C (OLED ฯลฯ) |
| `EEPROM` (object) | ไลบรารี IDE | read write update get put length | เล็ก ปลอดภัย |
| `SoftwareSerial` | ไลบรารี IDE | begin print println available read listen | บลูทูธ/โมดูลอนุกรม |
| ไลบรารีของเซนเซอร์ (DHT, IR remote, OLED SSD1306, ultrasonic ฯลฯ) | ไลบรารีภายนอก | — | **DEV-Q:** ใส่เฉพาะไลบรารีที่ตัวสร้างโค้ดใช้จริง (เกณฑ์ข้อ 2) ชื่อคลาส/เวอร์ชันต้องตรงกับที่ติดตั้งในแอป ไม่ใส่ล่วงหน้า |

- `SPI` `LiquidCrystal` `Stepper` ไม่อยู่ในตารางเซนเซอร์ → ไม่ใส่ใน MVP (เกณฑ์ "ที่ทีมรองรับ" ไม่ใช่ "ที่มีใน IDE ทั้งหมด") · ถ้าต้องการให้ครบ IDE = ขยายภายหลังได้โดยไม่เปลี่ยน UI
