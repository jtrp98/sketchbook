# Arm Lab: Feasibility R12–R15, R17 (ฟังก์ชัน 6A: ท่า · ข้อต่อ · แก้/อ่านท่า · เล่น · เมนูและคีย์ลัด)

ตรวจโดย ruler 2026-10-21 (R13 และ R15 ตรวจใหม่เฉพาะส่วนมือคีบ 2026-11-04 · หัวข้อย่อย "ตรวจใหม่ 2026-11-04") · ข้อมูล ENT และ BUG อ้างอิงจาก Architect เดิม (ตาราง BUG ดู `../feasibility.md`) · ความรุนแรง สูง/กลาง/ต่ำ ตาม CLAUDE.md

## R12: ท่าและท่าชุด
**ผล: ทำได้มีเงื่อนไข**
- ตรวจ: ท่า 0 แก้ไม่ได้ (UI ต้องบอกเหตุผล ไม่ใช่แค่จาง) · BUG-05 (tooltip G/K สลับ) แก้ตามโค้ด · ท่า 0 ≠ ท่าพัก ขัดกับ R16 (ดู `R5.md`)
- **เลิกทำ 6 วินาที (H3/H5 กลาง-สูง):** ลบ/ตัด/วางท่าหายถาวรเมื่อพ้น 6 วินาที · ป.1 อ่าน/ตัดสินใจไม่ทัน · WCAG 2.2.1 · context.md "ไม่มีแรงกดดันด้านเวลาโดยไม่จำเป็น" · เสนอให้ยืดหรือมีที่เก็บท่าที่ลบ (ประวัติ ENT-23 ปัจจุบันเป็นแค่ log) → OQ17 · BUG-11 (ลบท่าในตารางไม่ยืนยัน แต่ในแผงกด 2 ครั้ง) ต้องทำให้สม่ำเสมอ
- **ขาดนิยาม (กลาง):** (1) การเรียงลำดับท่า (ลาก? ปุ่มขึ้น/ลง? ต้องมีทางไม่ลาก WCAG 2.5.7) (2) ท่าชุด K####: สร้าง/แก้/เล่น/เด็กเข้าใจได้ไหม ใน requirement มีแค่สีและรหัส (3) จำนวนท่าสูงสุด (ขึ้นกับบอร์ด OQ14) (4) การเล่นเมื่อมีท่าเดียวหรือไม่มีท่า → เหตุผลที่ปุ่มเล่นปิด (5) BUG-09 `recoverYes` พังเมื่อท่า < 3 → OQ20 (1)(2)
- ENT ที่เกี่ยว (เดิม): ENT-14 ท่า (G####, ค่าข้อต่อ S0–S5, มือคีบ %, เวลา ms · แก้ที่ SCR-12 · ท่า 0 แก้ไม่ได้) · ENT-15 ท่าชุด (K####) · ENT-23 ประวัติ (การกระทำ เวลา)

## R13: ข้อต่อและขีดจำกัด
**ผล: ทำได้มีเงื่อนไข**
- ขีดจำกัดชัด (S0 ±180 · S1–S4 ±135 · มือคีบ 0–100% · 1000–9000 ms) ตรวจได้ แต่:
  1. **"ป้องกันหรือเตือน" กำกวม (H5 สูง):** ค่าที่พิมพ์เกินต้อง clamp, ปฏิเสธ หรือเตือนแล้วยอม? เมื่อค่ามีผลทันทีกับหุ่น (R14) การ "เตือนแล้วยอม" ส่งค่านอกขอบเขตไปหุ่นได้ → ข้อเสนอ: ไม่ส่งค่านอกขอบเขตไปหุ่นเลย (clamp + แจ้ง) → OQ17
  2. **ค่าระหว่างพิมพ์:** พิมพ์ "180" ผ่าน "1","18","180" ถ้าแต่ละการกดส่งคำสั่ง หุ่นกระตุก/ขยับผิด → ใช้ค่าเมื่อกดยืนยัน/ออกจากช่อง (Enter/blur) และกันช่องว่าง/ตัวอักษร/ทศนิยม/ลบอย่างเดียว/เลขไทย → OQ17
  3. **ขนาดก้าวไม่สม่ำเสมอ (BUG-11):** กดค้าง 3° vs พิมพ์/ลูกศร 1° · และอัตราการเกิดซ้ำตอนกดค้างต้องไม่ทำให้หุ่นขยับเร็วกว่าที่ปลอดภัยโดยไม่ผ่านเตือน 30° (สะสมหลายก้าว) → OQ17
  4. **ค่าเริ่มต้นไม่สอดคล้อง (BUG-06):** เวลาท่า 0 ตาราง 2000 vs `POSE0.t` 3000 · มือคีบท่าใหม่ 0% vs ท่า 0 50% (มือคีบเปลี่ยนฉับพลันเมื่อเล่นท่าแรก) · ต้องเลือกค่าเดียว Proposed: เวลา 3000 ทุกท่า · ท่าใหม่คัดลอกค่าจากท่าก่อนหน้า (ท่าแรก = ท่า 0) → OQ17
  5. หน่วย "ms" และ "°" สำหรับ ป.1 → แสดงเป็นวินาที (ดู `R1.md` R10) · ไฟล์ .ini ยังเป็น ms
  6. S0 ±180° ปลายทั้งสองห่าง 360° ผ่านหลังหุ่น: ท่าจาก +170° ไป −170° เป็นการหมุน 340° ไม่ใช่ 20° → นิยามของ "ไกลเกิน 30°" (ดู R15) ต้องไม่ใช้ระยะทางสั้นสุดแบบวงกลม
- ค่ามาจากข้อสมมติ 6A (Observed) · ขีดจำกัดจริงของ Pi/ฮาร์ดแวร์ ยืนยัน firmware (OQ1, OQ12) · ขีดจำกัดทางกลที่ไม่เท่ากันต่อข้อต่อ (S1–S4 ชน/ชนโต๊ะ) ไม่ระบุ

### ตรวจใหม่ 2026-11-04: มือคีบ (S5) เป็น % ไม่มีองศา · slider หนึ่งทิศ · ขั้น 5% / 1%
**ผล: ทำได้มีเงื่อนไข** (ไม่ขัดกับ R# อื่น · มีช่องว่างที่ต้องนิยาม 3 เรื่อง → OQ22, OQ23 · ไม่ block)
- **ขั้น 5% / 1% ไม่ขัดกัน:** 100 หารด้วย 5 ลงตัว (20 ขั้น) และ 1% เป็นจำนวนเต็มย่อยของ 5% → ค่าที่เก็บเป็นจำนวนเต็ม 0–100 เสมอ · จุดที่ยังกำกวมคือ **ค่าที่ไม่ลงตัว 5 แล้วกดค้าง** (เช่นพิมพ์ 47 แล้วกด +ค้าง) → Proposed: บวก/ลบ 5 จากค่าปัจจุบัน แล้ว clamp ที่ 0/100 (47 → 52 → … → 97 → 100) ไม่ snap เข้าตาราง 5 (เด็กเห็นเลขเปลี่ยนตามที่กด) · slider ลากต่อเนื่องใช้ความละเอียด 1% · คีย์ลูกศรบน slider = 1% ตรงกับช่องพิมพ์ → OQ23
- **อัตราซ้ำตอนกดค้าง (H5):** 5% ต่อก้าวมากกว่าเดิม (3° ของข้อต่อ) แต่ผลกระทบต่างกัน: มือคีบเปิด/ปิดเป็นจุดหนีบนิ้วเด็ก ไม่ใช่การกวาดแขน · ต้องคงอัตราซ้ำ (และเวลาเข้าท่า ≥ 1000 ms ของ R13) ไม่ให้ค่าไปถึง 0↔100% เร็วกว่าที่ servo ตามทัน (ส่งคำสั่งเมื่อปล่อยหรือจำกัดอัตรา) → dev/Designer · ข้อความอธิบายเรื่องนิ้วอยู่ที่ OQ24
- **ทิศของ % ไม่ได้นิยาม (H2/H5 กลาง):** 0% = เปิดหรือปิด? เมื่อตัดองศา/เลข 0 กลางแถบ แถบหนึ่งทิศต้องมีป้ายปลายแถบ ("เปิด/ปิด" หรือรูป) ไม่งั้น ป.1 ไม่รู้ว่า 100% คือคีบแน่น (ผลต่อของที่ถืออยู่) · ค่าเริ่มต้น ท่า 0 = 50% (ครึ่งหนึ่ง ไม่ใช่ขอบ) · ต้อง firmware/Designer ยืนยันทิศ → OQ23 · slider หนึ่งทิศ: ต้องไม่ใช้ตัวเลข 0 กลางแถบ (ตรงนิยาม) ตัวเลขแสดงเฉพาะปลาย 0% / 100% และค่าปัจจุบัน · aria-valuetext ต้องเป็น "50 เปอร์เซ็นต์" ไม่ใช่ "50 องศา"
- **BUG-06 (มือคีบท่าใหม่ 0% vs ท่า 0 = 50%):** ถ้าใช้ Proposed ของ OQ17 ข้อ (3) (ท่าใหม่คัดลอกท่าก่อนหน้า ท่าแรก = ท่า 0) มือคีบท่าแรก = 50% ไม่กระโดด 50→0 ตอนเล่นท่าแรก · แต่ **OQ17 ยัง open** ถ้าผู้ใช้เลือกค่าเริ่มต้นอื่น (เช่น 0%) เวลาเล่นท่าแรกมือคีบเปลี่ยน 50 ไป 0 ฉับพลัน และไม่เตือนเพราะ R15 ไม่นับมือคีบ → ต้องตอบ OQ17(3) ให้ครอบคลุมมือคีบ (เพิ่มประเด็นนี้ใน OQ17)
- **การแปลง % ↔ ค่าที่ส่งหุ่น / .ini (R7, R9) = ช่องโหว่หลัก (กลาง-สูง):** requirement ไม่ระบุสูตร (1) 6A สมมติ PWM 500–2500 (R2) แต่ servo มือคีบมักช่วงกลไกแคบกว่าข้อต่ออื่น (แมปเต็ม 500–2500 อาจสั่งเกินที่กลไกชน/มอเตอร์ค้างกินกระแส) → ต้องรู้ช่วงจริงของ S5 (OQ1/OQ12) (2) ไฟล์ .ini ของ Zide เก็บเป็นค่าอะไรของ S5 (PWM? มุม?) แปลงตรงกับ % ไหม · เปิดใน Zide ต้องได้ท่าเดียวกัน (R7) (3) ความละเอียด: 1% ≈ 20 PWM ถ้าแมปเต็มช่วง · .ini จาก Zide ที่ค่าไม่ลงตัว 1% (เช่น PWM 1537) นำเข้าแล้วปัดเป็น % จึงส่งออกกลับไม่ตรงเดิม (สูญเสียไม่เกิน ~10 PWM) → ยอมรับได้แต่ต้องบอกใน feasibility/ไม่ปัดเงียบเรื่องค่าเกินช่วง (4) **R9 นำเข้าค่าเก่า "เป็นองศา":** .ini/งานบันทึกที่ S5 เก็บเป็นองศา (ระบบเก่า/Zide) ไม่มีตัวบอกหน่วยในไฟล์ → นำเข้าตรง ๆ จะตีความผิด (เช่น 90 = 90% หรือ 90°) · งาน cloud ของ arm-lab ยังไม่มีผู้ใช้จริง (module `draft`, ไม่มี D#/built) จึงไม่ต้อง migrate ข้อมูลเดิม แต่ **ต้องใส่เลขเวอร์ชันสคีมา/หน่วยในงานที่บันทึกตั้งแต่แรก** เพื่อกันปัญหาในอนาคต · สำหรับ .ini ภายนอก: แปลงด้วยสูตรเดียวกับขาออก และปฏิเสธพร้อมบอกท่า/บรรทัดเมื่อค่าอยู่นอกช่วง S5 (ตามข้อเสนอเดิมของ R9 ใน `R6.md` ไม่ปรับเงียบ) → OQ22
- **ตารางลำดับท่า (`MainV6ASeq` คอลัมน์ S5):** แสดง "50%" ต้องใช้เลขเต็ม ไม่มีทศนิยม ไม่มี ° · ส่วนหัวคอลัมน์ต้องไม่สื่อว่าเป็นองศา (ระวังหัวตารางรวม "S0–S5 (°)") · ช่องพิมพ์ในตารางใช้กติกาเดียวกับช่องใน `MainV6AJoints`: รับ 0–100 จำนวนเต็ม พิมพ์ "%" ได้/ไม่ได้ต้องกำหนด (Proposed: ตัดเครื่องหมาย % ที่พิมพ์ ทศนิยม/ลบ/ตัวอักษร = ไม่รับ ค่านอกช่วง clamp+แจ้ง ตาม OQ17 (1)(2))
- ครอบคลุม state: H5 (ค่าเกินช่วงมือคีบ → clamp 0/100 + แจ้งเป็น "%") และ H1 (ท่าไม่ได้อยู่ที่หุ่น → slider ล็อกตาม R14 ใช้กับมือคีบเหมือนกัน) ✓

## R14: แก้ท่า อ่านท่าปัจจุบัน ประวัติ
**ผล: ทำได้มีเงื่อนไข (ฟีเจอร์ "อ่านท่าปัจจุบัน" ขึ้นกับ firmware)**
- ตรวจ "ต้องให้หุ่นอยู่ที่ท่านั้นก่อนจึงแก้ได้": ไม่ได้ระบุ (1) กลไก "ไปท่านั้น" (ปุ่ม? อัตโนมัติเมื่อเลือกท่า? ใช้เวลาเท่าใด? เตือนไกลเกิน 30°?) (2) สถานะ "กำลังไปท่า" (H1) และเมื่อไม่ถึงท่า/ไม่มี ack (3) แก้ท่าเมื่อยังไม่เชื่อม/หลุด (R16 ว่าแก้ไม่ได้ แต่ ST-19 ไม่ได้ระบุ → สรุปว่านักเรียนที่ยังไม่ต่อหุ่นสร้าง/แก้ท่าไม่ได้ ซึ่งขัดกับการเตรียมงานล่วงหน้าและอาจไม่ใช่เจตนา) → OQ17 ข้อ "แก้ท่าตอนยังไม่เชื่อม"
- **ปลดล็อกข้อต่อ (คลายแรงบิด) = ความเสี่ยงต่อมือเด็กและหุ่น (สูง):** แขนอ่อนตกตามแรงโน้มถ่วง โดยเฉพาะท่า 0 ตั้งตรง · มี "เตือน + นับถอยหลัง" แล้ว แต่ต้องกำหนด: ยกเลิกได้ระหว่างนับ · วิธีล็อกกลับ · ต้องประคองแขนก่อน · ตอนหลุดขณะแขนอ่อน (ล็อกกลับไม่ได้) · เปิดให้ ป.1–6 ใช้เองหรือเฉพาะโหมดครู → OQ18
- "อ่านค่าตอนคลายแขน" บน Pi ยังไม่ยืนยัน (OQ1/OQ12): ถ้าไม่ได้ ต้องถอดปุ่ม "อ่านท่าปัจจุบัน" และขั้นตอน "ปลดล็อก" ทั้งชุด (ลดความเสี่ยงไปด้วย) → ทางเลือกคือกรอกมุมเอง
- ต้องใช้คำ "อ่านท่าปัจจุบัน" (brand §7) · ประวัติ (ENT-23): เก็บที่ไหน นานเท่าใด ใครเห็น (เก็บเท่าที่จำเป็น NFR-05) ไม่ระบุ → ต่ำ ส่ง dev

## R15: การเล่น
**ผล: ทำได้มีเงื่อนไข**
- ตรวจ **"เตือนเมื่อสั่งขยับไกลเกิน 30°" (ST-23) ทำไม่ได้ตามข้อความปัจจุบันในบางกรณี (สูง):** ไม่ระบุว่า (ก) วัดต่อข้อต่อหรือรวม (ข) วัดจากไหน: ท่าก่อนหน้าในลำดับ หรือตำแหน่งจริงของหุ่น (ไม่ทราบหลังเชื่อมใหม่/แขนอ่อน/เชื่อมครั้งแรก) (ค) **ท่าสุดท้ายวนกลับท่าแรก** เมื่อเล่นหลายรอบ/วนไม่หยุด ไม่ปรากฏในลำดับแต่เป็นการเคลื่อนที่จริง (ง) มือคีบ (%) ไม่มีหน่วยองศา (จ) เตือนครั้งเดียวก่อนเล่นทั้งลำดับหรือทุกก้าว (เด็กกดผ่านจนชิน = เตือนแล้วไม่ได้ผล) ข้อเสนอ: ตรวจทั้งลำดับก่อนเริ่ม รวมท่าแรกจากตำแหน่งที่ไม่ทราบ (ถือว่าไกล) และท่ากลับ แล้วเตือนครั้งเดียวพร้อมลิสต์ก้าวที่ไกล → OQ16
- **ติ๊ก "ดูรอบหุ่นแล้ว" (ST-24):** ไม่ระบุว่ารีเซ็ตเมื่อใด (ทุกครั้งที่เล่น / ทุกเซสชันเชื่อม / เมื่อหลุด ST-48) → Proposed: รีเซ็ตทุกการเชื่อมต่อใหม่ + เมื่อแก้ลำดับท่าหลังติ๊ก → OQ16
- **เล่นจากบอร์ด/อัปโหลดลงบอร์ด (H1/H5/H9 สูง):** ไม่มีสถานะกำลังอัปโหลด (progress) · อัปโหลดล้มเหลว/หลุดกลางทาง → โปรแกรมบนบอร์ดค้างครึ่ง ๆ กลาง ๆ หรือเก่าของกลุ่มอื่น (หุ่นร่วมกันหลายกลุ่ม: "หุ่นกลุ่ม 3/5") · "เล่นจากบอร์ด" รันโปรแกรมที่ไม่ใช่งานบนจอ → ต้องบอก "โปรแกรมที่อัปโหลดล่าสุดเมื่อ…" และเขียนทับต้องแจ้ง · จำนวนท่าสูงสุดบนบอร์ด · เล่นต่อเองตอนเปิดไฟ (OQ14) · ST-21 ขณะ "เล่นจากบอร์ด": แอปไม่รู้ว่าหุ่นยังเล่นอยู่
- เลือกช่วงท่า/รอบ: ตรวจ (H5) ช่วงกลับด้าน/ว่าง · รอบ 0, 10, ว่าง, ทศนิยม · ลบท่าที่อยู่ในช่วงที่เลือก · แก้ลำดับขณะเล่น (ควรล็อกแก้ท่า/ลำดับขณะ ST-22) · วนไม่หยุด (ST-23) ต้องมีทางหยุดชัดและ ป.1 เข้าใจ "ไม่หยุดเอง" · ไม่ระบุว่ามีหยุดอัตโนมัติเมื่อไม่มีการใช้งาน
- **สถานะเล่นเสร็จ/หยุดผิดปกติ (H1):** ไม่มีสถานะ "เล่นจบ" / "หยุดกลางทางเพราะไม่ตอบ" ในรายการ ST → ควรเพิ่ม

### ตรวจใหม่ 2026-11-04: เตือน 30° ไม่นับมือคีบ
**ผล: ทำได้มีเงื่อนไข** (ตรรกะสอดคล้องกับ OQ16 · ความเสี่ยงใหม่ 1 ข้อ → OQ24 · ไม่ block)
- **ตรรกะ:** นับเฉพาะ S0–S4 ต่อข้อต่อตามเส้นทางจริง (S0 อ้อมหลัง) · สอดคล้องกับ OQ16 ข้อ (ง) ที่ระบุแล้วว่ามือคีบไม่มีหน่วยองศา · ตำแหน่งไม่ทราบ → ถือว่าไกลเสมอ (ไม่เกี่ยวมือคีบ) · ท่าที่ต่างกันที่มือคีบอย่างเดียว ไม่เตือน ✓ · ท่าสุดท้ายวนกลับท่าแรก/ลำดับก้าวที่ไกลในรายการเตือน แสดงเฉพาะ S0–S4 (ห้ามมีแถวมือคีบ "30°")
- **ปลอดภัยไหมถ้ามือคีบปิดแรงขณะถือของ (กลาง):** เหตุผลของเตือน 30° คือกวาดแขนไปโดนคน/ของ ซึ่งมือคีบไม่เข้าข่าย จึงยอมรับการไม่นับได้ แต่ความเสี่ยงของมือคีบเป็นคนละชนิด: (1) **หนีบนิ้วเด็ก** ตอนปิด โดยเฉพาะเวลา 1000 ms ที่สั้นสุด (2) **คีบเกินความกว้างของของ** servo ค้างดันของ กินกระแส/ร้อน (ไม่มีข้อมูลป้อนกลับ ไม่ทราบบน Pi) (3) **คลายมือคีบกะทันหัน** ทำของที่ถืออยู่ตก (เมื่อท่าแรกต่างจากท่าที่หุ่นอยู่จริง) · การเล่นทั้งลำดับยังต้องติ๊ก "ดูรอบหุ่นแล้ว" และป้ายท่าพักตาม ST-48 ซึ่งคลุมกรณีหุ่นยังไม่ถึงที่ ไม่มีการลดระดับป้องกันของข้อต่ออื่น → **ไม่ถือเป็นช่องโหว่ที่ block** · เงื่อนไข: popup "ดูรอบหุ่นแล้ว" มีข้อความถาวรให้เก็บนิ้วออกจากมือคีบ (ไม่ใช่เตือนเฉพาะกรณี) และถ้าบอร์ดรู้ว่ามือคีบเปลี่ยนมากภายในเวลาสั้นให้ Designer พิจารณาข้อความเสริมไม่ใช่เตือนแบบ 30° (ตัดสินที่ OQ24)
- **ขอบ/ความขัดกันของข้อความ:** R15 เดิมระบุ "(ง) มือคีบ (%) ไม่มีหน่วยองศา" เป็นปัญหาเปิด ตอนนี้ปิดด้วยการยกเว้นมือคีบ ✓ · ไม่มีจุดขัดกับ R5/R16 (ST-48 ใช้ตำแหน่งไม่ทราบ ไม่เกี่ยวมือคีบ)

## R17: เมนู ☰ และคีย์ลัด
**ผล: ทำได้มีเงื่อนไข**
- เมนู: รายการครบกับ my-work R5/R6/R9 ✓ · เมนูครูมีใน ☰ · "เกี่ยวกับ School Bot Studio" ✓
- **คีย์ลัดชนมาตรฐาน (BUG-10 · กลาง):**
  - **Mac ใช้ ⌘ ไม่ใช่ Ctrl** (HM5, HF15): requirement เขียน Ctrl+… ทุกตัว ต้องระบุการจับคู่ Windows Ctrl / Mac ⌘ และแสดงตามระบบ · ⌘H = ซ่อนแอป (ระบบ) ชนกับ "ประวัติ" และแอปมีปุ่ม "ซ่อน" ของตัวเองอยู่แล้ว (app-shell R2) · ⌘A = เลือกทั้งหมด ในช่องกรอกมุม/เวลา (R13) ซึ่งเป็นการใช้ปกติ · Ctrl+H ใน Windows = แทนที่ในหลายโปรแกรม (ชนน้อยกว่า)
  - ข้อเสนอ: เปลี่ยน "นำเข้า (Ctrl+A)" และ "ประวัติ (Ctrl+H)" เป็น shortcut อื่นที่ไม่ชนระบบ หรือไม่มี shortcut (ป.1–6 ไม่ได้ใช้คีย์ลัด) แต่คงรายการใน ☰ · คงคีย์มาตรฐาน S/N/O ตามหน้าที่เดิม (HM5)
  - **Esc หยุดหุ่นทั้งหมดตอนไม่มีอะไรเปิดอยู่ (Inferred):** ทิศทางปลอดภัย (หยุดคือด้านปลอดภัย) จึงควร**คงไว้เป็นทางลัดเสริม** ไม่ใช่ทางเดียว · กติกาที่ต้องเขียน: ในช่องกรอก Esc = ยกเลิกการแก้ค่า (ไม่หยุด) · มี dialog/popover เปิด Esc = ปิดสิ่งนั้น · ที่เหลือ Esc = หยุด · ห้ามเขียน "หยุดแล้ว" ถ้า firmware ไม่ยืนยัน (เหมือน R16) · ต้องแสดงบนปุ่มหยุด (tooltip ไม่พอ ไม่มี hover → ข้อความกำกับ) · Mac ผู้ใช้อาจกด Esc เพื่อออกเต็มจอ/ปิดอื่น → ต้องไม่ทำให้หยุดโดยไม่ตั้งใจจนเด็กงง (ไม่มีอันตราย แต่ต้องบอกสถานะ) · ปิดไว้ไม่ได้ block → OQ13 (ruler เสนอเพิ่ม)
  - ใน design ต้องไม่ให้ปุ่มหยุดหายหรือกดพลาดเพราะย้ายคีย์ลัด (ตามที่ OQ13 ระบุ)

## R14 รอบ 2026-11-11: อ่านท่าทีละข้อ (แก้ 2026-11-11 · OQ18 ข้อ 3)
**ผล R14: ทำได้มีเงื่อนไข** (ไม่เปลี่ยน · ตรวจโดย ruler 2026-11-11 · เฉพาะบรรทัด "อ่านท่าทีละข้อ" ข้อ (1)–(6) เทียบ R3, R5, R11, R15, R16, OQ1, OQ14) · ถาม AskUserQuestion ไม่ได้ในรอบนี้ (tool ไม่มีใน agent) → เปิด OQ104–OQ108 `open` ให้ session หลักถาม

**เงื่อนไขหลัก (firmware · ก่อนส่ง dev):** Pi ต้องทำได้ 3 อย่างที่ฉบับเดิมไม่ต้องใช้: (ก) ส่งค่ามุมแบบต่อเนื่อง (stream) ขณะคลายแรงบิด ไม่ใช่อ่านครั้งเดียว (ข) คลาย/ล็อกแรงบิด**รายข้อ** (ค) ล็อกที่ตำแหน่งปัจจุบันโดยไม่กระตุกไปค่าเก่า · ข้อใดทำไม่ได้ = ข้อ (1)–(4) ทำไม่ได้ทั้งชุด → ขยายคำถามของ OQ1 เป็น OQ106 · ไม่มีข้อที่ทำ UI ไม่ได้ถ้า firmware รองรับ

**สอดคล้องที่ตรวจแล้ว ✓:** R3 (ภาพแขนไม่ขยับ เปลี่ยนเฉพาะตัวเลข/สัญลักษณ์บนวงกลม ID) · R15 (ปลดล็อก/อ่านท่าไม่ใช่ trigger popup · การล็อกไม่ใช่คำสั่งขยับ) · (5) ไม่ใช้สีอย่างเดียว WCAG 1.4.1 · (6) ข้อความกลางตอนหลุดสอดคล้องหน้าจอประคองแขนของ R14/R16 และแถบเหลือง

**ช่องโหว่/edge case:**
1. **(สูง) "เลิกอ่าน" แล้วแขนไม่ขยับ = ค่าค้าง ขัดกับ "ค่าบนจอตรงกับหุ่นเสมอ":** ข้อต่ออ่อนจะทรุดตามแรงโน้มถ่วงช้า ๆ หรือค่า sensor สั่นเล็กน้อยโดยไม่มีมือบิด · ต้องนิยาม "เริ่มขยับ" (ค่าต่างจากค่าค้างเกินกี่องศา) ไม่งั้น dev ทำได้ 2 แบบที่ต่างกัน (ค้างตลอด vs สดทันที) · และข้อที่เลิกอ่านแล้วถือว่า "ยังไม่อ่าน" (ค่าเดิมทิ้ง) หรือไม่ → OQ104
2. **(สูง) สถานะผสม (บางข้อล็อก บางข้ออ่อน):** requirement มีทางจบโหมดทางเดียวคือ "ล็อกทั้งหมด" · ไม่ระบุ: ล็อกครบทีละข้อจนหมดแล้วจบโหมดเองไหม · ค่าที่อ่านเขียนลงท่าที่เลือก/ท่าใหม่/ไม่เขียน (เดิม "อ่านท่าปัจจุบัน" = ทั้งท่า) · กติกา slider ล็อก R14 "อ่านท่าสำเร็จ = รู้ตำแหน่ง" ใช้กับอ่านบางข้ออย่างไร · ระหว่างโหมดคลายแขน ไปท่านี้/เล่น/กลับท่าพัก/slider/มือคีบ ใช้ได้ไหม (สั่งขยับขณะบางข้ออ่อน = ข้อที่อ่อนไม่ตาม หรือ servo ล็อกกลับกระตุก) · ปุ่มหยุดระหว่างโหมดทำอะไร (ล็อกทุกข้อ? ส่งหยุดอย่างเดียว ข้อยังอ่อน?) · ออกจากหน้า/เปลี่ยนไฟล์/Ctrl+N ขณะบางข้ออ่อน (leave guard ของ R16 ครอบเฉพาะ "กำลังขยับ") → OQ105
3. **(กลาง) ข้อความถาวร "แขนล็อกอยู่ ห้ามบิดด้วยมือ" ขณะสถานะผสม:** ข้อความทั้งแขนไม่จริงเมื่อบางข้ออ่อน และสั่งตรงข้ามกับข้อที่ต้องบิด · ต้องผูกกับข้อ (เช่น ต่อข้อที่ล็อก) หรือแสดงเฉพาะเมื่อล็อกครบ → รวมใน OQ105
4. **(กลาง · H5) บิดมือเกินขีดจำกัด R13** (S1–S4 ±135, S0 ±180, มือคีบ 0–100%): ค่าสดเกินช่วงหรือ PWM นอก 500–2500 · ไม่ระบุว่า แสดงค่าจริง+เตือน, clamp บนจอ, หรือห้ามกด "อ่านท่า"/ล็อก · ล็อกที่มุมเกินช่วงแล้วบันทึกลงท่า = ท่าผิด R13 · มือคีบอ่านค่าเป็น % ตามสูตร R13 (ปัดตอนแสดง) ✓ → OQ107
5. **(กลาง) สายหลุดระหว่างคลายแขน:** (6) ครอบข้อความแล้ว ✓ · ค้าง: สัญลักษณ์ "ล็อกอยู่" บนวงกลม ID และค่าที่อ่านไว้ หลังหลุด ล้าง/คงไว้ (ไม่รู้ว่าหุ่นยังล็อกไหม ⟨OQ1/OQ14⟩) · หลังเชื่อมกลับ slider ล็อกตาม R14 อยู่แล้ว ✓ → รวมใน OQ105 (ข้อ ฉ)
6. **(กลาง · a11y) คีย์บอร์ด/ผู้อ่านจอของปุ่มอ่านต่อข้อ:** ปุ่มเดียวสลับป้าย "อ่านท่า"/"เลิกอ่าน" ต่อข้อ ต้องมีชื่อที่ระบุข้อ (เช่น "อ่านท่า S2") และบอกสถานะ (ล็อก/อ่อน) · ค่าสดห้ามประกาศต่อเนื่อง (aria-live สแปม) ประกาศเฉพาะเมื่อล็อก/เลิกอ่าน/ล็อกทั้งหมด · โฟกัสหลัง "ล็อกทั้งหมด" จบโหมด (ปุ่มหายไป) ต้องไปที่ใด · 6 ปุ่ม + ล็อกทั้งหมด + ยกเลิก ต่อจากปุ่มหยุดใน Tab order · ขนาดปุ่มตาม 6A (R1 ข้อยกเว้น ≥44px) ปุ่มต่อข้อเพิ่ม 6 จุดที่เด็กกดพลาดได้ (ข้อที่กดผิดแก้ได้ด้วย "เลิกอ่าน" ✓) · ไม่ใช่เรื่องผู้ใช้ต้องตัดสินทั้งหมด → ข้อกำหนดถึง crayon · ส่วนที่ต้องตัดสิน (ปุ่มเดียวสลับ vs สองปุ่ม · คีย์ลัด) → OQ108
7. **(ต่ำ) ปุ่ม "ยกเลิก" ระหว่างนับถอยหลังกับโหมดต่อข้อ:** นับถอยหลังคลายทุกข้อพร้อมกัน (ไม่ใช่คลายทีละข้อ) ✓ ตามข้อ (1) · ข้อที่ไม่ต้องการแก้ก็อ่อนด้วย → เด็กต้องประคองทั้งแขน · ยอมรับได้ตามฉบับเดิม (ไม่เปิด OQ)
