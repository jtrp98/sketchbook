# Arm Lab: Feasibility R1, R2, R3, R10 (ฐาน 6A · โปรโตคอล · แขนบนจอ · ป.1–6)

ตรวจโดย ruler 2026-10-21 · ป้ายหลักฐานดู `../../../context.md` · สรุปรวม/ตารางผลดู `../feasibility.md`

## R1: ใช้ 6A (MainV6A) เป็นฐาน
**ผล: ทำได้มีเงื่อนไข**
- ฟังก์ชันและ layout ของ 6A ผู้ใช้อนุมัติแล้ว (DEC-08) ฐานมี logic/state ครบ ทำต่อได้
- **ขัดกันเอง R1 ↔ R10 (กลาง):** R1 ห้ามทำหน้าใหม่ทั้งหน้า แก้ผ่านใบสั่งแก้เท่านั้น แต่ R10 + brand §2 บังคับ control/เนื้อหาหลัก ≥ 16px และเป้าสัมผัส ≥ 44px ขณะที่ MainV6A มี control 129/152 ตัวต่ำกว่า 16px (brand §2 "ค้างไว้") การแก้จริงเท่ากับจัด layout ใหม่ทั้งหน้า · ยึดลำดับ context.md (ความปลอดภัย > ป.1–6 ใช้เองได้ > สไตล์): R10 ชนะเรื่องขนาด/ข้อความ/ความหนาแน่น ส่วน R1 รักษา **ฟังก์ชัน พฤติกรรมความปลอดภัย (AC-07) และโครงสร้างหน้าจอ** → ต้องเขียนเป็นกติกาเดียว (OQ20)
- **ความจุหน้าจอ (Unknown):** พื้นที่ 1440×856 ไม่เลื่อนทั้งหน้า (app-shell R11) ต้องรองรับ เวทีหุ่น + ตัวแก้ 6 ข้อต่อ + ตารางลำดับท่า + แถบเล่น/หยุด + แถบแจ้ง ST-21 (ถาวร) + เว้นแถบล่าง 76px ของ dialog · เมื่อ control ใหญ่ขึ้น อาจไม่พอ · ตัดสินไม่ได้ด้วยการอ่านเอกสาร → Designer ลอง layout บน C1 ก่อน ถ้าไม่พอให้ย้อนมาถามผู้ใช้ว่ายอมเลื่อนเฉพาะแผงรายการหรือตัดข้อมูลรองใด (OQ20)
- พึ่งพา: ปุ่มหยุดห้ามถูกแถบหน้าต่างบัง (z 80 > `z-stop` 70) · app-shell OQ12 (CR-10 ทาง ก) ยังค้าง → ต้องเสร็จก่อนออกแบบ/ตรวจ ST-21 และ ST-22 ถือเป็นเงื่อนไข
- ตรวจ BUG-05–12 (ตารางใน `../feasibility.md`) ต้องปิดตอนปรับ · ที่กระทบความปลอดภัย/ค่าจริง: BUG-06, BUG-09, BUG-10, BUG-11

## R2: หุ่น Raspberry Pi โปรโตคอลใกล้เคียง Zide
**ผล: ทำได้มีเงื่อนไข (ขึ้นกับ firmware)**
- ข้อมูลอ้างอิง Architect (ARC-I04 ปิดแล้ว): ผู้ใช้ตอบ DEV-Q02 (2026-10-20) ใกล้เคียง Zide → คง 6A เกือบทั้งหมด · RSK-02 ปิดบางส่วน
- ยังเป็น Unknown ที่กระทบ UI โดยตรง: (1) "เล่นจากบอร์ด" (2) อ่านค่าตอนคลายแขน (3) คำสั่งหยุดและการตอบรับ (4) จำนวนท่าสูงสุดบนบอร์ด/ข้อมูลอัปโหลด (5) รายการค่าตั้งขั้นสูง (OQ12) · ถ้าข้อใดทำไม่ได้ ต้องตัดฟังก์ชันนั้นออกจาก R14/R15 และปุ่มที่เกี่ยวข้อง ออกแบบให้ถอดส่วนที่ขึ้นกับโปรโตคอลได้ (ตามที่ Architect เสนอ) → OQ1, OQ14
- **การเชื่อมต่อ USB บน Windows/Mac (R11) ต้องใช้ driver ไหม:** R11/app-shell OQ16 ระบุ "ไม่ต้องติด driver (ฝังใน installer)" ซึ่งอ่านได้สองทาง (ไม่ต้องใช้ driver / ฝัง driver แล้วติดอัตโนมัติ) ถ้าเป็นแบบหลัง เครื่องโรงเรียนที่ไม่มีสิทธิ์ admin อาจติดตั้งไม่ได้ (เหมือน RSK-A2 ของ Uno แต่ไม่ได้บันทึกสำหรับ Pi) → OQ14
- .ini ที่ export (R7) ต้อง "เปิดใน Zide ได้" ซึ่งขึ้นกับ OQ1 ว่าโครงสร้างค่าของหุ่น Pi ตรงกับ Zide
- ENT ที่เกี่ยว (ข้อมูลเดิม): ENT-14 ท่า · ENT-15 ท่าชุด · ENT-16 การตั้งค่าการเล่น · ENT-23 ประวัติ (รายละเอียดดู `R12.md`)

## R3: แขนบนจอไม่ขยับ
**ผล: ทำได้**
- ไม่มีการจำลอง ทำได้ตรงไปตรงมา ไม่เสี่ยงเทคนิค
- ข้อควรกำหนดให้ชัด (H1): รูปแขน/เวทีที่นิ่ง อาจทำให้เด็กเข้าใจว่าเป็นท่าจริงของหุ่น ต้องมีข้อความกำกับ (เช่น "ดูที่หุ่นจริง") ใกล้เวที และ **การไฮไลต์ "ท่าที่กำลังเล่น" ในลำดับท่าไม่นับเป็นการขยับแขน** ต้องยืนยันว่าทำได้ (Designer ตัดสิน บันทึกเหตุผล)
- เมื่อหลุด (ST-21) ตัวชี้ "ท่าปัจจุบัน/ที่กำลังเล่น" ต้องถูกล้าง เพราะแอปไม่ทราบตำแหน่งหุ่นอีกต่อไป (กันข้อมูลเท็จ · ตรงกับ R16)

## R10: UI เดียว ป.1–6 · WCAG 2.2 AA
**ผล: ทำได้มีเงื่อนไข**
- ไม่มีตัวช่วยเพิ่มสำหรับ ป.1–3 เป็นการยอมรับความเสี่ยงแล้ว (DEC-19 · RSK-04) จึงไม่นับเป็น block
- ข้อที่ Arm Lab ทำให้ ป.1 ยากเป็นพิเศษ ต้องมีทางออกใน design (ไม่ต้องเปลี่ยน requirement ยกเว้นข้อที่ระบุ OQ):
  - เวลาเข้าท่า "1000–9000 ms" และมุมองศาเป็นศัพท์/หน่วยที่ ป.1 ยังไม่ได้เรียน → แสดงเป็น "วินาที" (1–9) ใน UI และเก็บ ms ในไฟล์ (OQ17)
  - ค่าแก้ 3 ทาง (กดค้าง/พิมพ์/ลูกศร) ต้องมี target ≥ 44px และไม่พึ่ง hover · การเลือกท่าด้วยจุด S0–S5 บนเวทีเล็กต้องมีทางเลือกอื่น (แถบ ‹ ›)
  - การเรียงลำดับท่า (UJ-03 "เรียงลำดับ") ถ้าใช้การลาก ต้องมีทางเลือกไม่ลาก (WCAG 2.5.7 · context.md) · **requirements ไม่ได้ระบุวิธีเรียงลำดับ** (R12 ระบุแค่แสดงการ์ดหรือตาราง) → OQ20
  - ข้อความ hint/toast ≥ ~5 วินาที (AUD-F08) · ปุ่ม "เลิกทำ 6 วินาที" ของ R12 ต่ำกว่า/ใกล้เกณฑ์ และเป็นเวลาจำกัดที่ปรับไม่ได้ (WCAG 2.2.1) → OQ17
  - ข้อความถาวรของ ST-21 ต้องอ่านง่ายสำหรับ ป.1 และมีไอคอนคู่ข้อความ (ไม่ใช้สีอย่างเดียว) และบอกให้ "เรียกครู" ก่อนลงมือถอดสาย (R16 / OQ14)
- ตรวจไม่ได้ในเอกสาร ส่ง dev/highlighter: focus order, focus trap ใน dialog (ST-21 แถบ/ST-48 ล็อก), screen reader/role, ขยาย 200%, 3 ภาษา +40% (ข้อความ ST-21/ST-48 ยาว)
